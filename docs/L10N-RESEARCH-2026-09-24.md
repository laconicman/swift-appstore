# Localization research + design input — 2026-09-24

How dedicated translation engines accept context (directly and indirectly), an engine
bake-off, and a design proposal for a separate `AppStoreL10n` module. Produced from the
AppStore project's tool field trial; every vendor claim is from the engine's own
documentation, dated — engine APIs move fast, re-verify before building.

**Scope decision (owner, 2026-09-24):** two *distinct* workflows — App Store listing
metadata localization and app-string (.xcstrings) localization — sharing the provider
layer. Full bake-off rather than DeepL-only. No engine keys on hand → all live calls are
design-stage probes, not exercised.

**Constraints carried over:** draft → owner reviews diff → apply (D2); engine API keys
follow the same path-reference rule as ASC keys; no auto-applies.

## 1. Engine bake-off

| Engine | Direct context channels | Cost | Language coverage | Fit for us |
|---|---|---|---|---|
| **DeepL** | `glossary_id` (v3 editable, multilingual, grammar-flexing; 10 MiB) · `context` (free, unbilled — disambiguation only, **not** instructions) · `custom_instructions` (≤10×300 ch) · `style_rules` (stored) · `translation_memory_id` · `formality` · `tag_handling` · `model_type` | Free 500k ch/mo; Pro ~$25/1M | ~40; ES-419 exists | Best dedicated fit; see per-language gaps below |
| **Google Cloud Translation** | glossary (works with NMT *and* Adaptive, `contextual_translation_enabled`) · **Adaptive MT `referenceSentencePairs`** — ≤5 inline example pairs per request, or TSV/TMX dataset (5–30k pairs), no training | NMT $20/1M in; Adaptive $25/1M in + $25/1M out; 1 QPS adaptive | ~135 — broadest | Inline reference pairs = glossary+few-shot in one call; strong second |
| **Azure AI Translator** | dynamic dictionary (`<mstrans:dictionary>` forced replace, case-sensitive) · Custom Translator phrase/neural-phrase dictionaries | F0 free 2M ch/mo | ~135 | Custom model needs **≥10k segment pairs** — out of reach (~200 available). Standard+dictionary is a fallback path only |
| **Apple Translation** | **none** — text in, text out | free, on-device, private, no key | ~20+ incl. RU, ES(+MX) | Quality ceiling lower; draft-tier fallback; macOS-only for CLI |
| **LLM** (own call, or `translate_gpt` plugin) | everything in one prompt: glossary + style guide + field semantics + few-shot + placeholder rules | trivial at metadata volume; needs provider key | all | Richest channel; the only engine that handles CLDR plural sets and ASO-keyword semantics coherently. `fastlane-plugin-translate_gpt_release_notes` 0.5.0 already speaks OpenAI/Claude/Gemini/DeepL — pattern proof, unexercised |

### DeepL details worth building around (docs-verified 2026-09-24)

- **`context` is not a system prompt.** Vendor docs: it is for ambiguity resolution and
  short snippets — LLM-style instructions through it produce *unpredictable* output.
  Tone/rules go through `custom_instructions` or `style_rules` instead.
- **`custom_instructions` target coverage excludes Russian.** Allowed targets:
  `de, en, es, fr, it, ja, ko, zh` (+variants), requires `quality_optimized` model type.
  For `ru` the channel set degrades to glossary + context + formality.
- **Formality**: supported for RU, ES, ES-419 (target-only feature).
- **Glossaries are root-language**: a dictionary targeting `EN` applies to `EN-US`/`EN-GB`;
  create with root codes.
- **`/v3/languages`** reports per-language feature availability — drive capability
  decisions from it at runtime; never hardcode the matrix.
- **`context` and `tag_handling` markup are unbilled**; `show_billed_characters` returns
  the metered count for verification.

### Google Adaptive MT details

- `adaptiveMtTranslate` accepts `referenceSentencePairs` inline (≤5 per request, one list
  per content index) — or a named dataset (5–30k pairs, TSV/TMX). Inline mode needs no
  dataset lifecycle and matches our few-pair glossary scale.
- `contextual_translation_enabled` makes the glossary context-aware instead of literal
  find-and-replace.
- 1 QPS per project — fine for field-sized batches; batch fields per request anyway.

### Indirect context (engine-agnostic, works everywhere)

- **Placeholder masking** — protect `%@`, `%lld`, `{name}`, HTML/XML tags via
  `tag_handling` or pre-substitution; restore + verify echo post-translation.
- **Few-shot injection** — where supported natively (Google inline pairs, LLM prompt).
  Where not, post-edit glossary enforcement: verify output used glossary terms, flag
  violations for review.
- **Field bundling** — translate short fields (subtitle, name) with the English
  description passed as `context`, not as sibling `text[]` entries (texts in one request
  are translated *independently* — they do not share context with each other).

## 3. Per-field strategy (ASC metadata workflow)

| Field | Limit | Channels | Notes |
|---|---|---|---|
| `name`, `subtitle` | 30 ch | glossary + context + custom_instructions (es) / formality (ru) | brand locked via glossary |
| `keywords` | **100 UTF-8 bytes**, comma-separated | glossary + instructions | **not literal translation** — ASO term selection; Cyrillic doubles bytes; flag prose-shaped output for owner |
| `description`, `whatsNew`, `promotionalText` | 4,000 / 4,000 / 170 ch | all channels + few-shot from prior versions | marketing register |
| `supportUrl`, `marketingUrl`, privacy URLs | — | **passthrough, never translated** | — |
| `whatToTest` (beta) | — | glossary + context, literal register | instructions to testers |

Post-validation (existing `ListingValidator` rules + new): byte/char limits per field,
placeholder echo check, emoji rejection, URL passthrough check, glossary-term coverage
report (which locked terms survived).

## 4. App-strings workflow (distinct)

- Read `.xcstrings` JSON directly; translate missing/stale target entries; write back —
  the git diff is the owner-review surface.
- Catalog `comment` fields and key naming conventions feed `context`.
- **Plural caution**: `variations.plural` carries CLDR category sets — ru needs
  one/few/many, es needs one/many. MT engines return one form; LLM provider can produce
  the set. Rule: plural-bearing strings go to LLM provider or owner review, never plain MT.
- LearnWords catalogs on hand: `Localizable.xcstrings` (196 keys), `mul.lproj/Main`,
  `InfoPlist`, `ImportAsDictAction` — en/ru/es.

## 5. Proposed module — `AppStoreL10n`

Separate target in this package (owner's pick over folding into `AppStoreWorkflow`;
extractable to its own package later — LearnWords could consume `.product(name:
"AppStoreL10n", package: "swift-appstore")` for the strings workflow).

```swift
struct TranslationItem { key: String; sourceText: String; fieldId: String; placeholders: [String] }
struct ContextBundle {
    glossaryPairs: [(source: String, target: String)]   // engine-agnostic term map
    styleNotes: [String]                                // → custom_instructions / prompt lines
    fewShotPairs: [(source: String, target: String)]    // ≤5 for Google inline
    contextText: String?                                // DeepL context (free), LLM prompt section
    targetLocale: ASCLocale; formality: Formality?
}
struct TranslationResult { text: String; warnings: [String]; billedCharacters: Int?; providerTrace: String }

protocol TranslationProvider {
    var capabilities: ProviderCapabilities { get }      // per-target feature map
    func translate(_ items: [TranslationItem], context: ContextBundle) async throws -> [TranslationResult]
}
// DeepLProvider · GoogleAdaptiveProvider · LLMProvider · AppleTranslationProvider
// ContextAssembler (glossary mining from .xcstrings, few-shot selection by token overlap,
// placeholder mask/restore) · LocaleMap (ASC ↔ engine codes) · PostValidator
```

CLI surface suggestion: `asc l10n metadata` (inside the pull→diff→apply pipeline) and
`asc l10n strings` (xcstrings tool — usable from app repos).
